# Worked map: FamilyAI's journal + session-state subsystem

**Territory:** `Projects/FamilyAI` — specifically the objects a session
touches on startup and on the word "journal": the workspace bootstrap, the
workspace contract, the human journal store, and the session ledger. Not
"how FamilyAI works" (too broad) — this is the five-ish objects a new
contributor, or a fresh session, has to understand before touching
anything under `onboarding/hermes-template-config/` or `scripts/journal/`.

**Later reader:** primarily a model — a fresh Claude Code or Hermes
session that gets dropped into this repo mid-task with no memory of the
rename/reconciliation history. Secondarily, a human contributor picking
this subsystem back up after time away. Both arrive cold; this map is
written for the model case specifically because that is the actual,
recurring reader here.

**Method:** hand-built, no ICM Architect skill invocation this round —
`rules.md`/`identity.md` in this repo were written directly against this
week's brief rather than generated by the skill.

## Card: Workspace contract
**Source:** `onboarding/hermes-template-config/plugins/familyai-workspace/workspace_bootstrap.py:46-89` (`resolve_layout`, `save_contract`, `load_contract`, `is_bootstrapped`)
**Status:** Live

A plain dict — `root`, `journal`, `journal_state`, `projects`, `file_in`,
`file_out`, `bootstrapped_at`, `migrated_from`, `documents_link`, plus a
`version` int checked on load. Built by `resolve_layout()`, written by
`save_contract()` to `~/.hermes/familyai/workspace.json` (not under the
`~/AI` workspace itself — the contract lives in Hermes's own state dir,
one level outside the territory it describes). `load_contract()` refuses
anything whose `version` doesn't match, so a shape change here is a hard
break, not a soft one.

**Hits:** `familyai_workspace.py`'s `build_directive()` (reads `root`,
`journal`, `projects`, `file_in`, `file_out` directly out of the dict) →
the session-start injected system message every session sees →
`test_familyai_workspace_plugin.py`'s directive-content assertions. Also
hits *both* copies of `workspace_bootstrap.py` at once
(`scripts/workspace_bootstrap.py` and the plugin's own copy) —
`test_mirror_parity.py` asserts they stay byte-identical, so editing one
without the other is a guaranteed CI-visible failure, not a silent drift.

**Does not hit:** `JournalStore` or the session ledger's `ledger.py`.
Both take an explicit `journal`/`state` `Path` in their own constructor —
neither one reads `workspace.json` itself. The contract only tells the
*plugin* where those paths are; it is consumed once, at session start, and
never again downstream. It is easy to assume "the journal system" means
all three files move together — they don't.

## Card: JournalStore
**Source:** `scripts/journal/journal_store.py:57` (class `JournalStore`)
**Status:** Live

Owns the human-triggered journal: `JOURNAL.md`, `entries/`, and
`index.jsonl` under `<root>/Journal`. This is the *only* writer of those
three paths in the repo. Mirrored byte-for-byte (per
`test_mirror_parity.py`) into two packaged copies: the
`familyai-workspace` plugin and the `session-log` skill — both copies
exist because both consumers need the class available without a shared
importable package, not because there are two independent
implementations.

The same source file also defines `SessionLogStore` (line 192) — a
second class, sharing the file but not the output paths: `SessionLogStore`
writes `SESSION-LOG.md`/`session-log.jsonl` under
`Journal/state/session-log/`, disjoint from anything `JournalStore`
touches. One file, two nouns — don't assume "journal_store.py changed"
means the human journal changed; check which class.

**Hits:** its own two mirror copies (parity-enforced). The `session-log`
skill's runtime behavior (it constructs `SessionLogStore` from this same
file).

**Does not hit:** the session ledger (`ledger.py`) — different file,
different directory (`state/sessions/` vs `Journal/state/session-log/`),
no shared code path.

## Card: Session ledger
**Source:** `onboarding/hermes-template-config/skills/session-ledger/ledger.py:95-152` (`append_event`, `read_session`)
**Status:** Live

Per-session event log: one `<session_id>.ledger.json` file per session
under `<state>/sessions/`, written by `append_event()`, read back by
`read_session()`. This is the ledger the `session-log` skill watches for
milestone-shaped events (per its `SKILL.md`) — it is upstream of
`SessionLogStore`, not the same store.

**Naming collision** (see `reference/`): "session log" (the milestone
narrative in `SESSION-LOG.md`, owned by `SessionLogStore`) and "session
ledger" (the raw per-session event file, owned by `ledger.py`) are two
different objects one folder apart. Easy to conflate; don't.

**Hits:** `session-log`'s milestone watcher (reads these events to decide
what to narrate).

**Does not hit:** `JournalStore` / the human journal — no import, no
shared path.

## Card: `auto_journal.py` filename
**Source:** `onboarding/hermes-template-config/skills/session-log/auto_journal.py`
**Status:** Leftover

The skill folder was renamed `auto-journal` → `session-log` (identifier
rename only — folder name, `SKILL.md`, dependent skills' `requires:` — so
the word "journal" belongs exclusively to the human-facing trigger). The
Python file inside it kept its original name, `auto_journal.py`, and its
internals were deliberately left untouched. This is a genuine, working,
live file — the leftover is purely the filename no longer matching its
parent folder's name. Flagged here so a later reader doesn't "fix" the
mismatch by renaming the file and breaking the mirror-parity pair with
`scripts/skills/auto_journal.py`.

## Card: `familyai journal` CLI
**Source:** none — referenced only in prose (planning notes, prior journal
entries describing this subsystem's still-outstanding gaps)
**Status:** Ghost

No file, script, or entry point of this name exists anywhere in the repo
(`grep` across `scripts/` and `onboarding/` finds nothing). It shows up
as a named "still to build" item in planning discussion, which is exactly
the ghost pattern rule 3 warns about: if this map had listed it as live
because the name is familiar, a later reader would try to invoke a
command that isn't wired to anything.
