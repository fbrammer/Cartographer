# Worked map: AgentSwarm's dispatch layer

**Territory:** `Projects/AgentSwarm` — specifically the objects a session
touches when it dispatches a task: the provider router, the role config,
the provider clients it can route to, and one stale reference left behind
by an earlier design. Not "how AgentSwarm works" (too broad) — this is
the handful of objects a new session has to understand before adding or
routing a role, self-contained to this one project.

**Later reader:** primarily a model — a fresh Claude Code session picking
up AgentSwarm to dispatch a task, with no memory of how the provider
routing evolved. Secondarily, a human contributor auditing what actually
calls what before changing `roles.json`. Both arrive cold.

**Method:** hand-built, no ICM Architect skill invocation this round —
`rules.md`/`identity.md` in this repo were written directly against this
week's brief rather than generated by the skill.

## Card: `call()` dispatcher
**Source:** `orchestrate.py:46-53`
**Status:** Live

Takes a role dict (from `roles.json`) and a message list, and branches on
`role["provider"]`: `"openrouter"` → `or_client.call()`, `"hermes"` →
`hermes_client.call()`, `"gemini"` → `gemini_client.call()`. Anything else
raises `ValueError`. This one function is the entire routing layer —
every subcommand (`cmd_run`, `cmd_retry`, model-refresh's `call_fn`) goes
through it rather than importing a provider client directly.

**Hits:** whichever provider client the role's `"provider"` field names,
selected fresh on every call — there is no caching or role-to-client
binding beyond this one dict lookup.

**Does not hit:** the two provider branches whose client no current role
actually selects (see the leftover card below) — those code paths exist
and would run correctly if reached, but nothing in `roles.json` reaches
them today.

## Card: `roles.json`
**Source:** `roles.json` (11 entries, checked directly)
**Status:** Live

Flat map of role name → `{provider, model, hermes_provider?,
reasoning_effort?}`. Every single one of the 11 current entries
(`coder_fast`, `coder_cheap`, `coder_heavy`, `checker_hermes`, three
`research_assistant_*`, four `gemini_*`) sets `"provider": "hermes"` —
confirmed by grepping the file for `"provider"` values, not by reading
the AGENTS.md description of it. `model_refresh.py`'s `refresh-apply`
subcommand is the only thing that rewrites this file at runtime (via
`save_roles`); everything else only reads it.

**Hits:** `call()`'s provider branch selection for every dispatch. The
periodic model-refresh flow (`cmd_refresh_apply` → `model_refresh.
apply_coder_refresh`/`apply_researcher_refresh`), which reads and
rewrites this file directly.

**Does not hit:** `or_client.py` or `gemini_client.py` at runtime, as
things stand — see the leftover card. Adding a role with
`"provider": "openrouter"` or `"gemini"` would change that; today,
nothing does.

## Card: `hermes_client.py`
**Source:** `hermes_client.py`, referenced from `orchestrate.py:38,50`
**Status:** Live

The only provider client any current `roles.json` entry actually reaches
— wraps the local `hermes` CLI, passing both `-m <model>` and
`--provider <hermes_provider>` explicitly (per AGENTS.md's documented
finding that omitting `--provider` silently lands on the wrong model via
Hermes's generic fallback chain). `model_refresh.py`'s `call_fn` also
routes through this client specifically, not through `call()` — the
refresh flow only ever needs to smoke-test candidates against Hermes.

**Hits:** every one of the 11 `roles.json` entries' actual network call.
The model-refresh smoke test.

**Does not hit:** `or_client.py`, `gemini_client.py` — no import edge
between them; each provider client is independent, `call()` is the only
thing that knows all three exist.

## Card: Unused provider clients
**Source:** `or_client.py`, `gemini_client.py`
**Status:** Leftover

Both are real, complete, independently working clients — `or_client.py`
for OpenRouter, `gemini_client.py` for the plain Gemini API — and both
are still imported by `orchestrate.py` and wired into `call()`'s branch
logic. Neither is dead in the sense of being broken or orphaned: both are
documented in AGENTS.md as deliberate escape hatches (`or_client.py` for
any future role that sets `"provider": "openrouter"`; `gemini_client.py`
kept "as a manual escape hatch" after Gemini-family roles were re-routed
through Hermes on 2026-07-24 for its fallback-chain value). The leftover
is specifically that **zero of the 11 current `roles.json` entries reach
either one** — confirmed by grepping `roles.json` for `"provider"`
values, all 11 say `"hermes"`.

A reader who sees these two files imported and assumes they're
load-bearing today would be wrong; a reader who deletes them because
they look unused would break the documented escape-hatch design.

## Card: `run_checker`
**Source:** none — named only in `orchestrate.py:16`'s module docstring
("...see run_checker's old docstring reasoning")
**Status:** Ghost

`grep -n "run_checker\|def cmd_"  orchestrate.py` finds the one docstring
mention and nothing else — no function, class, or import of that name
anywhere in the file. The same docstring (lines 11-16) explains why: an
earlier design had a configured "checker" model and a dedicated
check/retry/finalize loop in Python; the current design moved that
judgment into the Claude session driving the script instead, and
`cmd_run`/`cmd_retry`/`cmd_finalize` are what's left — primitives only,
no built-in judgment. The docstring's own cross-reference to
`run_checker` is a pointer to a function that no longer exists. A reader
searching the file for "how does checking work" who trusts that
cross-reference literally will go looking for code that was removed.
